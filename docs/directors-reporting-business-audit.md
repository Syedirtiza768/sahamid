# Directors' Reporting: business audit and coverage map

Audit date: 5 November 2026, Asia/Karachi. This is a repository/code audit, not a new assertion about production balances. Historical database counts in the earlier reconciliation packs are explicitly dated August/October 2026 and must not be presented as today's position. No operational data was changed for this audit.

## Evidence and scope

The application is a customized webERP, with a company database selected by the authenticated ERP session. Root accounting/inventory reports, `v2` operational reports, `v3` sales-performance reporting, and the additive `bi/` layer share operational tables. The audit used the active menus, BI registry, source services, schema dump, and existing reconciliation evidence together. No AGENTS.md was found in the application tree outside dependencies and the nested historical worktree.

The machine-readable companion `directors-reporting-route-inventory.csv` records every quoted PHP route found in `MainMenuLinksArray.php`, `v2/reportLinks.php`, `v3/reportLinks.php`, and `bi/Reports/ReportRegistry.php`, including the source menu and occurrence count. `directors-reporting-source-inventory.csv` records report candidates' statically detected SQL sources and request parameters. These inventories are discovery aids: conditional entries, PHP duplicate array keys, dynamic routes, included SQL, wrappers, and table names assembled at runtime mean literal route counts are not counts of distinct authorized reports.

Snapshot counts before the dashboard changes: root menu 268 PHP route literals / 264 distinct strings; v2 hub 117 / 116; v3 hub 110 / 110; BI report registry 92 / 91. These include maintenance and transaction routes. The checked-in structure has 510 ordinary `CREATE TABLE` statements plus a temporary view-definition stub; the reporting semantics are principally PHP/SQL. Do not reuse the older catalog's report counts as a fresh completeness claim.

Detailed earlier evidence remains useful, with the limits stated in each pack:

- `docs/BI_REPORT_CATALOG.md`, `docs/BI_ROUTE_REGISTRY.md`, `docs/ARCHITECTURE_MAP.md`: module/route/model inventory.
- `docs/BI_RECONCILIATION_INVOICE_AR_GL.md`, `docs/BI_RECONCILIATION_AR.md`: invoice tax-basis, allocation, GL and receivable differences.
- `docs/BI_RECONCILIATION_SHOP_SALES.md`: completed POS, CRV/CSV, ledger/header/component distinctions.
- `docs/BI_RECONCILIATION_PIPELINE.md`: native stage keys, multiplicity, pending-DC, date and owner issues.
- `docs/BI_RECONCILIATION_INVENTORY_MPIW.md`, `docs/BI_RECONCILIATION_PROCUREMENT_PAYABLES.md`: inventory snapshots, receipt/accounting/physical bridges, active custom purchasing.
- `docs/SALES_REPORTING_IMPLEMENTATION.md`, `docs/SALES_REPORTING_DECISIONS.md`: later sales-event capture, fiscal/workday calendar, event-time attribution, frozen report evidence and remaining provisional policies.

## Dimensions and boundaries

| Dimension | Where supported | Required treatment |
|---|---|---|
| Company | ERP authenticated database/session | No client-selected database; no cross-company sums without a separately authorized consolidation source. |
| Customer / branch | Invoice, debtor transaction, case, order; `custbranch` composite `(debtorno,branchcode)` | Join by the complete key. Customer branch is not company branch. |
| Location | `locstock.loccode`, movement location, invoice dispatch location | Apply only to facts carrying that meaning; do not pretend it filters GL or AP without lineage. |
| Department / cost center | GL tags and expense tab types/GL groups where populated | Label the actual source dimension; a tag is not a universally captured department. |
| Product / category / brand | Invoice/component/stock/receipt lines + stockmaster | Aggregate at correct line grain first; missing master records remain visible. |
| Salesperson / team | Case owner, shop entered owner, current branch owner, captured sales events/team history | Keep meanings separate; prohibit filters outside caller's server-derived scope; preserve historical event attribution where captured. |
| Project | Case reference, contract and optional transaction metadata | Case is an opportunity reference, not a complete project-cost ledger. Project profitability needs linked revenue and historical costs. |
| Supplier | Supplier ledger and MPIW; planning supplier may be missing | Preserve unlinked receipts as exceptions instead of dropping their value. |
| Currency | Source/customer/supplier currency and transaction rates | Retain raw amount and basis, convert only with valid recorded rates; flag invalid/unavailable conversion and never add unlike currencies. |

## Definition conflicts and data-quality findings

1. **The same commercial event appears at several workflow stages.** Case/order/OC/DC/invoice/POS must stay separate facts. Existing “business volume” composites are operational views, not accounting revenue. Joining all stage detail tables before aggregation causes multiplicative fan-out.
2. **Invoice value has two valid but different bases.** Published BI detail formula and debtor ledger `ovamount` differ by GST behavior. Tax-policy exceptions remain diagnostic; hard-coded 0.83/1.17 conversions in historical reports cannot define global net sales.
3. **Declared keys exceed many existing joins.** OC requires PO key; customer branch requires debtor key; shop components require order plus selling-line key; invoice detail/options require invoice/line/option. The schema uses surrogate keys on invoice and case documents, so nominal document-number uniqueness should be checked, not assumed.
4. **Open/settled/reversed are not interchangeable.** Prior reconciliation found settled residuals, open reversed supplier rows, missing allocation endpoints and stored-vs-allocation discrepancies. Summary and detail must share one predicate, with residual/settlement exceptions visible.
5. **Due, expected, invoice, posting and receipt dates answer different questions.** Missing/zero dates must have explicit status. As-of balances cannot be produced by filtering transaction date while subtracting today's allocations.
6. **Master attributes can rewrite historical interpretation.** Case owner is a text name, invoice/DC owner fields are often blank, current branch owner differs materially from shop entered owner, and old team CSV membership cannot prove historical responsibility. New captured commercial events have stronger provenance; do not synthesize it for legacy rows.
7. **Procurement's real populated model is custom.** MPIW receipt lines, supplier transactions, payment ledger and IGP are linked but not guaranteed one-to-one. Adding bridge rows duplicates amounts. `bazar_parchi.paid` and `shopsale.paid` were not dependable settlement measures in prior evidence.
8. **Planning source completeness is limited.** Existing procurement details had many zero quantities/prices and absent ETA dates; reorder completion linkage was previously reported weak. An unpriced row is an unknown commitment, not a zero-value order. Correcting operational statuses requires workflow-specific validation; a dashboard must not rewrite them.
9. **Current stock is not historic stock or historic cost.** `locstock`, latest movement `newqoh`, and cart issuance can diverge. Standard valuation cost includes labour/overhead. Different item units cannot be meaningfully added; zero/negative costs and negative quantities need separate exception counts/values.
10. **Cash, expense and profit need separate ledgers.** ASSIGNCASH is funding transfer. Petty cash can include local purchases and balance-sheet claims. Bank transactions include transfers and require two exchange rates. Net receipt/payment activity is not operating cash flow or free cash flow without classification.
11. **GL linkage was not authoritative for operational AR in prior evidence.** The August audit recorded disabled debtor-to-GL linkage and a questionable configured debtor control account, plus chartdetails vs gltrans variance. The current dashboard must expose/recheck control configuration; it cannot silently certify that prior issue is resolved.
12. **Duplicate presentation is extensive.** v2/v3 copies, old/Copy/numbered/Redo variants, filters/API fragments, print/PDF/CSV wrappers and compatibility library entries do not establish independent metrics. `Reorder Level PS` is declared twice in the v2 PHP array, so only the later key renders.

## Missing reporting and data capture

Immediate query/interface gaps that can be closed with existing records are native-grain cross-domain aggregation, shared comparison date windows, explicit source-period contracts, unified summary/detail/export predicates, currency validation, drill rows, ranking contributors, data-quality counts, source latest dates and clear partial failure states. Reuse existing services and namespaced BI conventions rather than inventing another accounting formula.

The following require prospective governed capture or external evidence; the dashboard must retain an unavailable or estimated state until that evidence exists:

- **Approved revenue/COGS/expense classification and fiscal configuration:** map account groups without guessing from account numbers or names; reconcile date GL to period statements; record fiscal calendar and budget approval/coverage. A chosen fiscal-month setting alone is not historical accounting certification.
- **Historical inventory / gross margin:** store approved cost-at-sale and sale-cost linkage or reconstruct from validated movement costing. Today's stockmaster cost is only an explicitly labelled estimate.
- **Forecast and cash availability:** bank statement/integration freshness, opening/available/restricted balances, transfer pairing, expected customer receipt dates, payment plans, supplier commitments, scenario assumptions and confidence.
- **Targets:** effective-dated amount, currency, measure/tax basis, owner/team, approved period and reviewer. Current annual salesperson targets have no history; pro rata is an estimate.
- **Project/department performance:** validated cross-module department/project keys on both revenue and expense; current case/tag alone does not provide full departmental/project P&L.
- **Sales funnel history:** enquiry response/outcome, issued quotation/revision, PO receipt, follow-up and event-time team history. Existing `bi/Commercial` migrations/capture already implement much of this prospectively and should be reused when installed; unsupported historical gaps remain visible.
- **Manufacturing/assets/service operations:** establish whether each supported legacy module is in use, reconcile its records and register meaningful measures before treating empty tables as successful operating performance.

## Comparison, navigation and reconciliation requirements

- Current/comparison periods must disclose start/end and calendar day counts. Previous-period is equal elapsed days; month/quarter/year comparisons clamp invalid dates. Fiscal YTD follows the configured year start, with previous fiscal elapsed period and leap-day treatment explicit.
- Partial current month/quarter/year should compare comparable elapsed prior time, and the UI must disclose clamping. Custom comparison may have different durations; do not disguise unequal exposure as a growth rate.
- Absolute change is current minus comparison. Percentage change is unavailable when the comparison is zero or missing; a zero result remains a known zero. Credit/negative-baseline changes require an explicit mathematical denominator/basis and direction labels that do not assume every increase is good.
- Stocks (current AR/AP/on-hand/cart), flows (invoice/receipt/expense/bank activity), and forecasts cannot share an implied date contract. Where historical stock cannot be reconstructed, disable its delta and explain why.
- Filter chips and source dimensions must disclose which facts each filter affects. Drill and export must carry the same period/comparison, dimension keys, status, search/sort and server permission checks; summary totals must be independently reproducible from the same eligible grain.
- Reconcile line → document → month/customer/person totals, source currency → valid base currency, positive balances/credits → net ledger, and detail/export row count → summary count. Missing dimensions remain in an explicit bucket.
- The existing `SessionAuthorizationAdapter`, `AuthorizationContext`, page tokens and domain-specific scopes are not interchangeable grants. A director permission can allow cross-business oversight only within the current authorized company; it must not let ordinary sales-dashboard users see unrelated finance/AP/expense rows. Drill-through and exports need the same enforcement as summaries. Source links retain their existing access checks.
- Large tables must aggregate in SQL with bounded dates and allowlisted filters/sorts, paginate detail, cap exports with visible truncation/limits, and expose query failure separately from no records. Cache keys must include database, permission scope, definitions and all filters; failed partial results must not be cached as complete.

## Audit validation limits

This audit verified code and declared schema, not current production data. Existing dated reconciliation packs provide historical examples and regression targets. No runtime, database or deployment claim follows from this document. Live validation must check important formulas, current schema readiness, scoped summary/detail/export parity, record-link journeys, query plans and realistic volume before release. The final implementation report must list which of these checks actually ran and which remain constrained by the available environment.
